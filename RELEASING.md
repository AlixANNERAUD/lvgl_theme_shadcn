# Releasing

Releases are automated with [release-plz](https://release-plz.dev) using a Release PR flow. One release publishes the
Rust crates to crates.io, tags `vX.Y.Z`, creates the GitHub release and publishes the C library to the PlatformIO
registry.

## Packages

- `lvgl_theme_shadcn`: the safe Rust crate. It is tagged `vX.Y.Z` and gets a GitHub release. The tag and the release
  also stand for the C library.
- `lvgl_theme_shadcn_sys`: the raw FFI crate, which ships and compiles the C sources. It is published to crates.io
  together with `lvgl_theme_shadcn`, and has no tag or GitHub release of its own.
- The C library: [PlatformIO](https://registry.platformio.org/libraries/alixanneraud/lvgl_theme_shadcn) package,
  plus the `CMakeLists.txt`, `library.properties` (Arduino) and `idf_component.yml` (ESP-IDF) manifests, all
  consumed from the `vX.Y.Z` tag.

Everything shares a single version, defined in `[workspace.package]` in the root `Cargo.toml`.
`lvgl_theme_shadcn` depends on `lvgl_theme_shadcn_sys` with an exact `=X.Y.Z` requirement and the two crates are
always bumped together (`version_group` in `release-plz.toml`). `scripts/sync-version.sh` copies the Cargo version
into `CMakeLists.txt` (`project(... VERSION X.Y.Z)`, without any pre-release suffix), `library.json`,
`library.properties` and `idf_component.yml`. The `Rust` and `Release` workflows fail if the crate versions, the pin
or any C manifest diverge.

## Flow

1. Changes are merged to `main`. CI runs, nothing is published.
2. The `Release` workflow opens or updates a Release PR that bumps the version, updates `CHANGELOG.md` and
   `Cargo.lock`, then runs `scripts/sync-version.sh` on the PR branch and pushes a
   `chore: sync c manifest versions` commit when the C manifests need it.
3. Review the Release PR. Edit the version or the changelog in the PR if needed. When editing the version, update
   `[workspace.package].version` and the `=X.Y.Z` pin of `lvgl_theme_shadcn_sys` together, then run
   `scripts/sync-version.sh` and commit the C manifests.
4. Merge the Release PR when a release is wanted. The `Release` workflow then validates the workspace (version
   consistency, tests against LVGL, `cargo package`), publishes `lvgl_theme_shadcn_sys` then `lvgl_theme_shadcn` to
   crates.io, creates the `vX.Y.Z` tag and the GitHub release with the changelog of that version, and finally calls
   `publish-platformio.yml` to publish the C library to PlatformIO.

Ordinary merges never publish: `release_always = false` restricts publishing to merged Release PRs. If validation
fails, nothing is published.

## Recovering a failed release

- Validation fails after the Release PR is merged: nothing was published. Fix the problem with a normal pull request.
  The next Release PR then carries the version that was never published, and merging it publishes. Re-running the
  failed workflow does not help, because it replays the same commit, and `release_always = false` prevents publishing
  from any commit that is not a merged Release PR.
- The crates are published but the PlatformIO publish failed: use "Re-run failed jobs" on the `Release` run, which
  keeps the version output of the release job. Alternatively, start `publish-platformio` by hand from the Actions tab
  with `version` set to `X.Y.Z`. Re-running the whole workflow does not work, because `releases_created` is then
  false and the PlatformIO job is skipped.

## SemVer policy

Pull requests are squash-merged, so each pull request title becomes one commit on `main`. The `PR Title` workflow
requires titles to follow [Conventional Commits](https://www.conventionalcommits.org) (`feat: ...`, `fix: ...`,
`feat!: ...`). Merge commits, release commits and version sync commits are left out of the changelog.

The proposed bump is derived from these commits since the last release:

| Commit | `>= 1.0.0` | `0.x.y` |
| --- | --- | --- |
| `fix:` and other types | patch | patch |
| `feat:` | minor | patch |
| `feat!:`, `fix!:` or `BREAKING CHANGE:` footer | major | minor |

[cargo-semver-checks](https://github.com/obi1kenobi/cargo-semver-checks) runs on the Release PR and reports public
Rust API breaking changes in the PR body. If it detects a breaking change, the bump is raised accordingly. It does not
see the C API: mark C breaking changes with `!` in the pull request title. The maintainer has the final say and may
change the version in the Release PR.

## Changelog

`CHANGELOG.md` is generated by release-plz with git-cliff using the `[changelog]` section of `release-plz.toml`. It
covers the commits since the previous release that release-plz attributes to either crate, and its entry for the
release is used as the Release PR content and the GitHub release body. Review it in the Release PR and add C-only
changes by hand if they are missing.

## PlatformIO

`.github/workflows/publish-platformio.yml` is called by the `Release` workflow after a release (a GitHub release
created by release-plz with `GITHUB_TOKEN` does not trigger other workflows). It checks that the C manifests match the
Cargo version and the released version, packs the library with `pio pkg pack` and publishes it to the
[PlatformIO registry](https://registry.platformio.org/libraries/alixanneraud/lvgl_theme_shadcn) under the
`alixanneraud` owner.

It can also be started by hand from the Actions tab (`workflow_dispatch`), optionally with the expected version. The
registry rejects a version that already exists.

## Required setup

- Repository secret `CARGO_REGISTRY_TOKEN`: a crates.io API token with the `publish-new` and `publish-update`
  scopes.
- Repository secret `PLATFORMIO_AUTH_TOKEN`: log in with `pio account login`, create a token with
  `pio account token`, then add it under **Settings > Secrets and variables > Actions** or with
  `gh secret set PLATFORMIO_AUTH_TOKEN`.
- **Settings > Actions > General > Workflow permissions**: enable "Allow GitHub Actions to create and approve pull
  requests".
- Optional repository secret `RELEASE_PLZ_TOKEN`: a fine-grained personal access token limited to this repository
  with `Contents` and `Pull requests` read and write permissions. The `release-plz-pr` job uses it to open the Release
  PR and to push the C manifest sync commit, which makes CI run on the Release PR including that commit. Without it
  the job falls back to `GITHUB_TOKEN`, and pull requests opened and commits pushed with `GITHUB_TOKEN` do not
  trigger other workflows.
